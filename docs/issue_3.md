## 目的

別のDBMSへ移植する前に、**EASが正確に再現している中止規則を使う実用上の理由があるか**を検証する。前回は「同じEAS policyを計算する実装同士」の高速化を示したが、元のAriaよりバッチ全体は遅かった。今回は、もっと安い別policyも含め、選択時間・確定件数・バッチ全体の費用を比較する。

実装、独立検査、実測、生データ、再現手順、日本語報告、後続調査への判断材料まで完成させる。EASの勝利も敗北も前提にしない。先のチャットで示したPythonによる件数比較も、追試対象であり正解データではない。

## 1. 比較対象

### 新規の2方式（C++で実装）

**`accept_id`**

取引ID昇順に一度走査する。既に採用した取引が使うキーと `S_t` が交わらなければ採用し、キーを使用済みにする。そうでなければ不採用。**不採用取引はキーを予約しない。** 空集合の取引は採用する。

**`accept_static_degree`**

初期状態の異なる競合相手数 `d0(t)` を正確に一度だけ計算する。`(d0昇順, ID昇順)` にソートし、その順に `accept_id` と同じ「採用済みとの非競合」検査をする。採用/不採用のたびに次数・順位を更新しない。

2キーでは `d0({a,b})=C(a)+C(b)-C({a,b})-1`。1キーは `C(a)-1`。同一キー集合を持つ別取引は別人として数え、自己は数えない。3/4キーは包除による一回計数でよい。**初期次数の計数・索引構築・ソートを無料にしない。** 2キー専用の軽いsingleton/pair計数でもよいが、独立な全相手交差と照合する。

`accept_id`に不要なsubset index/profile/graphを作らせない。共通APIの都合だけで高価な前処理やEAS固有のsubset容量制限を課して、安い方式を不当に遅くしない。共通の論理キー正規化、安全性検査、実入力の抽出費用は全方式について扱いを明示する。

### 既存方式

- `native`：元のAria。SI=false、reordering=trueを維持。
- `adaptive` EASの **k=1を主比較**、k=2を前回との接続・過剰中止の対照にする。既存policy自体は変更しない。
- 既存`graph/lazy/profile`は、後述の代表条件で同一policyの対照・内訳確認に使う。全実験の直積に増やさない。

同じキーの2取引でk=2が全件中止になる例を残す。k=1との対照なしで「EAS全体が悪い」と結論しない。逆に、k=2に最低一件確定する補正を黙って追加しない。

### 比較グループを正しく分ける

`policy`（native、accept_id、accept_static_degree、EAS+k）と `implementation`（graph/lazy/profile/adaptive）を結果形式で区別する。

- 同じEAS・同じkの実装間：全中止round、commit mask、正規化した証明書の一致を要求。
- 異なるpolicyや異なるk：結果は違ってよい。各々の安全性と品質・費用を比較する。
- 新しい採用方式は、採用検討順・不採用ID・commit mask等を保存すればよい。EASの中止roundを偽装しない。旧runnerの「非native全方式は同一決定」という検査を、policyごとの検査へ修正する。

なお、完全RMWのnative Ariaは「各キーについて全取引中で最小IDのwriterである取引」を確定する規則であり、**後で中止される取引の予約も残る**。`accept_id`は「採用済みとの競合」だけを見るのでnativeとは違う。元のAriaを書き換えて同じものにしない。

## 2. 正しさ・品質の独立検査

1. 小さな全列挙と固定seed randomで、新2方式を独立な素朴実装と比較する。staticの初期次数は全相手との集合交差で検証する。空入力、空集合、同一集合の別取引、同値キーの別アドレス、大きなキーID、同点、重複操作、全員競合/非競合を含める。
2. 全方式で確定取引のキーが相互に素であることを直接検査し、既存の実Aria上のsnapshot・private writes・最終DB全状態の逐次再実行検査を通す。異なるpolicyの最終状態を相互一致させる必要はない。
3. 新2方式について、不採用取引を一つ追加できないという「極大性」を小入力で確認する。極大と最大を混同しない。EASには無条件に同じ性質を要求しない。
4. 小入力（目安n<=18、予算を先に固定）では取引部分集合の全探索で**最大確定件数**を求め、各policyの最適値との差を示す。2キーの問題はキーを頂点・取引を辺とするmatchingに対応するが、大入力の最適値を測ったと推定しない。大型solverやDBMSの導入は不要。
5. EASがstaticより多く確定する例と、その逆の例を、事前に固定した有限の列挙/random範囲で探す。見つかったものは最小化・保存し、構造を説明する。見つからなければ探索範囲を報告し、一般の優越性を主張しない。人工反例は機構の説明用であり、実用workload上の優位の証拠とは分ける。
6. `T1={a,b}, T2={a,c}, T3={b,d}`のnative/EAS差、frozen top-k、ゼロcommit等の既存回帰testを維持する。worker=1/2/4・連続バッチのsmoke、ASan/UBSanを実行する。

## 3. 実験計画（最小限）

計画・seed・反復数・予算を先にファイルへ保存する。

| 系列 | 条件 |
|---|---|
| 主比較 | 既存mainの2キー・n=128/512/2048/8192/32768・一様/Zipf 0.99・worker=1。native、新2方式、adaptive k=1/k=2を同じ入力で比較。 |
| 補助arity | 1/3/4キー・n=8192・一様/Zipf 0.99・worker=1。主比較と同じ5方式。 |
| 同一policyの対照 | 2キー・n=8192・一様/Zipfと、全員同じ2キー・n=4096。EASのgraph/lazy/profile/adaptiveをk=1で比較し、主比較との対応を確認。 |
| 並列の最小確認 | 2キー・n=8192・Zipf・worker=2/4で主比較5方式。worker=1は主比較を流用。 |

各条件は上記5入力seed、各seedで独立な時間測定3反復を基本とする。入力による変動と同一入力の計測変動を分離し、15個の独立入力と数えない。paired比較は同一trace・同一反復に対応させ、まずseed内の時間変動を要約する。別々の中央値の商だけで結論しない。

新旧を同一binary、同一機械・compiler・flags・affinity条件で再測定し、過去の別実行時間を混ぜて速度比を計算しない。測定順をseed付きで入れ替え、高負荷な方式を同時実行しない。保存したウォームアップ方式の限界を明記する（別プロセスのwarmupが次プロセスのheap/cacheを暖めたとは主張しない）。

費用の扱い：

- 実Ariaの実R/W set抽出・正規化 → 必要な構築/ソート/選択 → mask/証明書生成・解放までをselector全体として測る。
- snapshot開始 → 全確定書込み適用完了をbatch全体として測る。nativeの既存判定、共通取引本体、reservationの扱いは前回と揃える。
- 取引本体、値サイズ、入力・DB初期化の扱いは全方式共通。安全性/全状態検査は測定外。
- 時間、commit/abort数、peak RSS、構築/ソート/更新の内訳、EASの再質問・切替え回数を保存する。新方式で不要な計数は0またはnot_applicableとする。
- `commit_count / batch_seconds`を一バッチの**有効処理率**として併記する。時間が短いだけ/件数が多いだけで勝者にしない。これは再試行を含む定常throughputや公平性の証明ではない。
- commit=0は0として扱い、成功取引当たり費用は未定義/無限と明記する。timeout/OOM/unsupportedは失敗statusとして残す。

## 4. 分析と次の判断

**A. policy保存の価値**：EAS同士の同一判断の高速化は維持できたか。

**B. policyを選ぶ価値**：安い方式に対して、EASはどの条件で何件多く確定し、そのために何ms追加で使ったか。件数と時間の二軸で比較し、「安い方式が同数以上で速い」「EASの件数は多いが追加費用が大きい」「EASが有効処理率でも上回る」を区別する。差の小さい結果・ばらつき・例外を残す。

**C. 重い取引の可能性**：一バッチで速くなかっただけで、全ての本体費用・再試行モデルについて不利と断言しない。件数利得が残る場合、worker=1について均一の追加本体コストcを各試行へ加える感度分析 `commit_count/(measured_batch_time+n*c)` を作り、採用方式との逆転点の有無を示す。このcは仮定であり実測でない。新しい重い取引workloadやretry engineの実装は本Issueでは不要。実用上その費用があるかは後続Issueで確認する。

このIssue中に別DBMSへ移植しない。EASが不利な結果でも、証明を否定したことにしたり、勝つworkloadが出るまで探索を無制限に増やしたりしない。
